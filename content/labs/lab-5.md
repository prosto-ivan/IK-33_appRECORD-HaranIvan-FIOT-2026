# Лабораторна робота №5: Безпека та продуктивність серверних додатків

**Тема:** Безпека Node.js-додатків, оптимізація запитів, кешування та тестування API.

**Мета:**  
Навчитися забезпечувати базову безпеку Node.js-додатків, оптимізувати продуктивність REST API, використовувати кешування для зменшення навантаження на сервер, а також виконувати тестування та аналіз продуктивності backend-застосунку.

---

## ⚙️ Завдання 1. Створення та запуск REST API на Node.js та Express

**Було необхідно:**
- використати серверний застосунок на базі Node.js та Express;
- переконатися, що REST API успішно запускається;
- перевірити доступність основних маршрутів API.

**Результат:**
У роботі було використано існуючий backend-застосунок `LinkEduHub`, реалізований на Node.js та Express. Сервер запускається на порту `3000`, підключається до бази даних, синхронізує таблиці та надає доступ до REST API.

Після запуску сервера у консолі відображається повідомлення про успішне підключення до бази даних, синхронізацію таблиць і старт сервера за адресою `http://localhost:3000`.

![Запуск сервера](/assets/labs/lab-5/server_start.png)

## 🛡 Завдання 2. Реалізація захисту API

**Було необхідно:**
- підключити `Helmet` для захисту HTTP-заголовків;
- реалізувати `rate-limit` для обмеження кількості запитів;
- додати валідацію даних за допомогою `express-validator`;
- перевірити, що API коректно реагує на некоректні запити.

**Результат:**
Для підвищення безпеки серверного застосунку було підключено бібліотеку `Helmet`. Вона додає до відповідей сервера захисні HTTP-заголовки. У проєкті було вимкнено лише `contentSecurityPolicy`, оскільки frontend використовує inline-обробники подій у HTML, наприклад `onclick`.

Також було реалізовано обмеження кількості запитів за допомогою `express-rate-limit`. Це дозволяє захистити API від надмірної кількості запитів з одного IP. Якщо користувач або бот надсилає забагато запитів, сервер повертає помилку з повідомленням про перевищення ліміту.

Додатково було реалізовано валідацію даних для маршрутів створення та редагування ресурсів. Сервер перевіряє, щоб назва ресурсу мала мінімум 3 символи, URL був коректним посиланням, а `type_id` був числовим значенням.

## 💾 Завдання 3. Реалізація кешування відповідей

**Було необхідно:**
- реалізувати кешування відповідей API;
- зменшити кількість повторних звернень до бази даних;
- перевірити, що перший запит отримує дані з БД, а повторний запит отримує дані з кешу.

**Результат:**
Для кешування відповідей у серверній частині було використано бібліотеку `node-cache`. Кешування реалізовано для маршруту `GET /api/resources`, який повертає список навчальних ресурсів.

Під час першого запиту сервер звертається до бази даних, отримує список ресурсів і повертає відповідь із позначкою `source: database`. Після цього отримані дані зберігаються у кеш.

![Перший запит до ресурсів з бази даних](/assets/labs/lab-5/resources_database.png)

Під час повторного запиту сервер уже не звертається до бази даних, а повертає раніше збережені дані з кешу. У відповіді вказано `source: cache`, що підтверджує роботу кешування.

![Повторний запит до ресурсів з кешу](/assets/labs/lab-5/resources_cache.png)

Таким чином, кешування дозволяє пришвидшити повторні запити та зменшити навантаження на базу даних.

## ⚡ Завдання 4. Оптимізація маршруту API

**Було необхідно:**
- оптимізувати один із маршрутів REST API;
- зменшити кількість зайвих звернень до бази даних;
- зменшити обсяг даних, які повертає сервер;
- покращити швидкодію роботи API.

**Результат:**
Для оптимізації було обрано маршрут `GET /api/resources`, який використовується для отримання списку навчальних ресурсів у каталозі.

Оптимізація маршруту була виконана за рахунок двох підходів. Перший підхід — використання кешування через `node-cache`. Після першого запиту список ресурсів зберігається у кеші, тому повторні запити можуть виконуватися без додаткового звернення до бази даних.

Другий підхід — обмеження кількості полів, які повертаються з бази даних. У Sequelize-запиті було використано параметр `attributes`, завдяки чому сервер отримує тільки потрібні поля ресурсу: `resource_id`, `title`, `url`, `type_id`, `created_by` та `createdAt`.

![Оптимізація маршруту ресурсів у коді](/assets/labs/lab-5/resources_route_optimization.png)

Після внесення змін маршрут продовжує коректно повертати список ресурсів, але працює ефективніше. Повторні запити можуть повертати дані з кешу, що зменшує навантаження на базу даних і пришвидшує відповідь сервера.

![Результат роботи оптимізованого маршруту](/assets/labs/lab-5/resources_optimized_result.png)

## 🧪 Завдання 5. Тестування API

**Було необхідно:**
- провести тестування API;
- перевірити працездатність основних маршрутів серверного застосунку;
- використати інструменти автоматизованого тестування;
- переконатися, що API повертає коректні відповіді.

**Результат:**
Для тестування API було використано бібліотеки `Jest` та `Supertest`. У проєкті було створено файл тестів `tests/api.test.js`, у якому перевіряється робота основних маршрутів серверного застосунку.

Було протестовано такі endpoints:
- `GET /api/status` — перевірка стану сервера;
- `GET /api/resources` — отримання списку навчальних ресурсів;
- `GET /api/meta/resource-types` — отримання типів ресурсів.

Після запуску команди `npm test` усі тести були виконані успішно. Це підтверджує, що основні маршрути API працюють коректно та повертають очікувані дані.

![Код автоматичних тестів API](/assets/labs/lab-5/api_tests_code.png)

![Успішне виконання тестів API](/assets/labs/lab-5/api_tests_success.png)

## 📈 Завдання 6. Аналіз продуктивності до та після оптимізації

**Було необхідно:**
- провести аналіз продуктивності REST API;
- перевірити роботу маршруту під навантаженням;
- порівняти поведінку API до та після оптимізації;
- оцінити вплив кешування та rate-limit на роботу сервера.

**Результат:**
Для аналізу продуктивності було використано інструмент `Artillery`, який дозволяє виконувати навантажувальне тестування API. Для перевірки було обрано маршрут `GET /api/resources`, оскільки він використовується для отримання списку навчальних ресурсів і є одним із основних маршрутів застосунку.

Спочатку було перевірено роботу API з активним обмеженням кількості запитів. Під час навантажувального тестування сервер повернув відповіді зі статусом `429`, що означає перевищення дозволеної кількості запитів. Це підтверджує, що механізм `rate-limit` працює коректно та захищає API від надмірного навантаження.

![Перевірка rate-limit через Artillery](/assets/labs/lab-5/artillery_rate_limit.png)

Після цього ліміт запитів було тимчасово збільшено, щоб перевірити продуктивність маршруту без блокування. Повторне тестування показало, що сервер успішно обробляє велику кількість запитів до маршруту `/api/resources`. Завдяки кешуванню повторні звернення можуть оброблятися швидше, оскільки сервер не виконує запит до бази даних кожного разу.

![Навантажувальне тестування API через Artillery](/assets/labs/lab-5/artillery_performance.png)

Отримані результати показують, що оптимізація маршруту через кешування зменшує навантаження на базу даних, а `rate-limit` додатково захищає API від великої кількості запитів з одного джерела. Таким чином, серверний застосунок став більш стабільним і краще підготовленим до роботи під навантаженням.
